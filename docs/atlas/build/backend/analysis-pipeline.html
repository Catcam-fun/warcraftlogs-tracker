Analysis Pipeline

POST /api/analyze runs one generator in backend/app.py: sign in, roster, reports, fights, duplicate pulls, deaths, processing, result.

01

Summary

  • POST /api/analyze (backend/app.py:109) reads its JSON body, checks the bearer token, then returns a streaming response driven by the inner generate() function (backend/app.py:122). Everything on this page happens inside that generator. The stream format is on backend-api-endpoints.
  • The raid key (selectedRaid) is the main input. It selects the allowed boss encounter IDs (RAID_ENCOUNTERS, backend/analysis.py:234) and the tier's date window (RAID_DATE_WINDOWS, backend/analysis.py:262).
  • WarcraftLogs is read in a fixed order: token, roster, report list, each report's light fight list, the full fights of the reports that keep pulls, then each report's talent loadouts, deaths and defensive events. The client functions live in warcraftlogs.
  • Finished reports are served from cache instead of WarcraftLogs; see backend-caching-and-limits. Slot and wipe rules are on backend-death-counting.
02

How it works

The generator yields a progress event at each stage. Click each step to see what it does.

Raid selection

analyze_fights (backend/analysis.py:302) is the gate that decides which pulls exist at all. When the raid key is in RAID_ENCOUNTERS, a fight is kept only if its boss encounter ID is in that raid's set and its difficulty equals the requested one (backend/analysis.py:313). This is what isolates one Midnight raid from the others that share a WarcraftLogs zone, and what keeps Mythic+ dungeon bosses out of mixed reports (comment at backend/analysis.py:227). Only an unknown raid key falls back to filtering by fightZone and difficulty (backend/analysis.py:318).

resolve_report_window (backend/analysis.py:280) treats the tier window as the outer bound. A user start date is used only if it is later than the tier start, and a user end date only if it is earlier than the tier end (backend/analysis.py:289). A None tier end means the tier is still open, so the user's end date (or none) is used. An unknown raid key passes the user's dates through unchanged (backend/analysis.py:287).

Duplicate pulls

When several raiders log the same night, each report contains the same pulls. is_duplicate_pull (backend/analysis.py:66) keeps, per boss ID, a list of the pulls already accepted. A new pull is a duplicate when it overlaps an accepted one by at least 15 seconds, or by at least 50% intersection-over-union (backend/analysis.py:57, backend/analysis.py:58). Overlap uses absolute times (report start plus fight offset, backend/app.py:255), so it works across reports. Two logs can start the same pull at the same millisecond (the same log uploaded twice); copies are taken by start time, then report code, then fight id, so the same copy is kept on every run (backend/analysis.py:94). A copy cut short gives way to the longest one: across 1,543 pulls logged by several raiders, copies' lengths differed by under 0.1 s 99% of the time, and cut-short copies were 5-84 s shorter (TRUNCATED_COPY_MS, backend/analysis.py:81). One cut-short copy (a wipe whose logger stopped at 173 s) had none of the pull's 21 deaths.

Per-report query order

fetch_report_deaths (backend/app.py:338) sends one query at a time, in an order picked for WarcraftLogs' point cost:

  1. Talent loadouts (defensives.fetch_combatants, backend/app.py:376). The first event query on a report pays a higher "cold" price. Loadouts are the cheapest way to pay it (about 2 points); Deaths or Casts sent first cost 4-17. The report then stays warm for only 10-30 seconds, so the queries that follow are sent right after.
  2. Deaths (get_report_deaths_bulk, backend/app.py:379).
  3. Skip check: counted_by_fight finds the deaths that can count (backend/app.py:325). With none, the report returns empty defensive data and no hits (backend/app.py:388); nothing would read them.
  4. Defensive events: casts, buffs and healing, with the loadouts from step 1 passed in so they are not read twice (backend/app.py:398).
  5. Instant kills (backend/app.py:408), then death windows (backend/app.py:416).

After the first query, the rest cost about a quarter less sent one by one than all at once (comment at backend/app.py:393). A loadout read that fails is recorded as the report's defensive error, and the deaths are still read (backend/app.py:377).

The bulk death query

get_report_deaths_bulk (backend/analysis.py:357) asks for every Deaths event between the first kept pull's start and the last one's end in one GraphQL request (backend/analysis.py:383). With cheat deaths on, the same request uses GraphQL aliases to also fetch Debuffs filtered to CHEAT_DEATH_DEBUFF_IDS and Healing filtered to CHEAT_DEATH_HEAL_IDS (backend/analysis.py:388, backend/analysis.py:395). Each block that has a nextPageTimestamp is followed page by page (backend/analysis.py:475, backend/analysis.py:329).

Deaths are grouped by fight id, but only for fights that survived filtering and dedup (backend/analysis.py:490, backend/analysis.py:634). Each death records its timestamp, targetID, the player name from the report's actors, and the killing ability's id and name (backend/analysis.py:648).

Cheat deaths

A cheat death is a lethal hit the player survived because of an effect such as Cheat Death or Cauterize. backend/features.py lists the effects: debuffs left on the saved player (backend/features.py:14) and two saves that show only as a heal on them, Guardian Spirit and Ardent Defender (backend/features.py:26). An applydebuff of a listed debuff, or a heal from a listed heal spell, becomes a cheat-death event (backend/analysis.py:522).

Two cleanup passes follow. First, only the earliest cheat death per player per fight is kept (backend/analysis.py:552). Second, events for the same player and ability within 100 ms of each other are merged (backend/analysis.py:583). Later, drop_saves_that_died removes saves the player died from within 5 seconds; see backend-death-counting.

What the result carries

The result shape is listed on backend-api-endpoints. Two parts come straight from this pipeline: events holds every guild member's death and cheat death with its slot and inWipe, counted or not, and pullParticipation holds every pull each main character was present for, keyed "<reportId>_<fightId>" (backend/app.py:525). The results page counts deaths against those pulls; see frontend-results-view.

06

Invariants

Must

keep only fights whose boss encounter ID is in RAID_ENCOUNTERS for the selected raid; the zone filter is a fallback for unknown raid keys only (backend/analysis.py:313).

Must

let user dates only narrow RAID_DATE_WINDOWS, never widen it (backend/analysis.py:280).

Must

drop duplicate pulls before fetching deaths, so a pull logged by three raiders is counted once (backend/app.py:269).

Must

sort pulls by start time, then report code, then fight id, so the copy of a pull that is kept never depends on which report was read first (backend/analysis.py:94).

Never

cache the deaths of a report that failed to load; get_report_deaths_bulk re-raises (backend/analysis.py:705) and the cache write happens only after a successful result (backend/app.py:382).

07

Gotchas

!Reports are not filtered by zone›

get_guild_reports fetches by date only, because WarcraftLogs gives each report one zone and a raid night mixed with dungeons can be filed under the dungeon zone (backend/warcraftlogs.py:176). The encounter allowlist does the filtering.

!Open tiers page through everything since their start›

a None end date means no upper bound. Only the newest tier (Midnight Season 2, backend/analysis.py:265) is open; Midnight Season 1 ends 2026-08-23 (backend/analysis.py:269), and a test fails if an older tier is left open (backend/test_raid_selection.py).

!The first log of a pull wins, unless it was cut short›

dedup keeps whichever report's copy starts earliest (report code first on a tie), unless another copy lasts more than 5 s longer (backend/analysis.py:84). A copy only a little shorter is kept even if it misses a few seconds. A log that can't be read in full also gives way (backend/app.py:278).

!A report with no death that can count reads no defensives›

it returns after the deaths query (backend/app.py:386), so its defensive data is empty, not missing, and it does not show in the "defensive details missing" warning.

!Cheat-death dedup works within one report›

get_report_deaths_bulk runs once per report, so its passes (first per player per fight, then same player and ability within 100ms, backend/analysis.py:577) only see that report's events; the same pull in another report was already dropped by is_duplicate_pull.

!One save per player per pull›

the first cleanup pass keeps only the earliest cheat death per player per fight (backend/analysis.py:552), so a player saved twice in one pull shows one cheat death.

!Failed reports are left out, not counted as deathless›

a report that throws returns empty death lists (backend/app.py:434), so the processing loop skips its pulls after numbering them (backend/app.py:496); otherwise they would add attended pulls with no deaths and lower everyone's death rate. test_unreadable_report_adds_no_pulls checks it.

!Unreadable defensive data is a warning, not an error›

deaths still count; the stream sends a progress message naming how many reports lack detail (backend/app.py:463).

08

Glossary

iRaid key›

the selectedRaid string, such as manaforge, that indexes RAID_ENCOUNTERS and RAID_DATE_WINDOWS.

iFinished report›

a report whose end time is more than two hours ago; only these are read from or written to the caches.

iDuplicate pull›

the same boss pull in another raider's log, found by time overlap.

iCheat death›

a lethal hit the player survived because a listed effect fired.
